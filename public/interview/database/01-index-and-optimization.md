# 01 索引原理与优化

> **难度**：⭐⭐⭐⭐⭐  
> **出现率**：99% 必考  
> **核心**：B+ 树底层 → 索引分类 → 失效场景 → 实战优化

---

## 一、为什么需要索引？

类比：**一本没有目录的书 vs 有目录的书**。

- 无索引：全表扫描，时间复杂度 O(n)
- 有索引：B+ 树查找，时间复杂度 O(log n)

**面试金句**：
> 索引的本质是「**用空间换时间**」，通过额外维护一个有序的数据结构，把查找的时间复杂度从 O(n) 降到 O(log n)。

---

## 二、为什么选 B+ 树？（高频）

### 2.1 候选数据结构对比

| 结构 | 查找 | 范围 | 缺点 |
|------|------|------|------|
| 哈希表 | O(1) | ❌ 不支持 | 无法范围查询、排序 |
| 二叉搜索树 | O(log n) | ✅ | 容易退化为链表 |
| 平衡二叉树 (AVL) | O(log n) | ✅ | 树太高，磁盘 IO 多 |
| B 树 | O(log n) | ✅ | 数据散落各层，范围查询要回溯 |
| **B+ 树** | **O(log n)** | **✅** | **最适合磁盘存储** |

### 2.2 B+ 树的三大优势

1. **矮胖**：非叶子节点只存索引（不存数据），单页可存更多键 → 树高度低（通常 3-4 层即可存千万数据）→ 磁盘 IO 少
2. **范围查询友好**：叶子节点是双向链表，范围扫描直接顺序遍历
3. **查询稳定**：所有查询都到叶子节点，I/O 次数可预期

### 2.3 一棵 B+ 树能存多少数据？

> 经典问题：**3 层 B+ 树能存多少数据？**

```
假设：
  - 每页 16KB
  - 主键 BIGINT (8B) + 指针 (6B) = 14B/键
  - 一页可存 16 * 1024 / 14 ≈ 1170 个键
  - 数据行 1KB → 一个叶子页存 16 行

3 层 B+ 树：1170 × 1170 × 16 ≈ 2200 万行
```

**结论**：千万级数据表，主键查询只需 3 次 IO。

## 三、聚簇索引 vs 非聚簇索引（必考）

### 3.1 概念对比

| 项目 | 聚簇索引 (Clustered) | 非聚簇索引 (Secondary) |
|------|---------------------|----------------------|
| 别名 | 主键索引 | 二级索引/辅助索引 |
| 叶子节点存什么？ | **整行数据** | **主键值** |
| 一张表有几个？ | 1 个 | 多个 |
| InnoDB | 主键 = 聚簇索引 | 普通索引 = 非聚簇 |

### 3.2 回表（关键概念）

```sql
-- 表结构
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50),
  age INT,
  KEY idx_name (name)
);

-- 查询
SELECT * FROM user WHERE name = '张三';
```

**执行过程**：
1. 走 `idx_name` 二级索引 → 找到 `name='张三'` 对应的主键 id
2. 拿主键 id **回到聚簇索引** → 找到完整行数据

→ 走了 **两棵 B+ 树**，称为「**回表**」。

### 3.3 覆盖索引（避免回表）

```sql
-- 仅查 name 和 id 字段
SELECT id, name FROM user WHERE name = '张三';
```

`idx_name` 的叶子节点已经存了 name 和 id，**不需要回表**，称为「**覆盖索引（Covering Index）**」。

**面试加分项**：
> 在 EXPLAIN 中看到 `Extra: Using index` 就表示触发了覆盖索引。覆盖索引是最重要的优化手段之一。

## 四、联合索引与最左前缀（必考）

### 4.1 最左前缀原则

```sql
KEY idx_abc (a, b, c)
```

可用索引的查询：
- ✅ `WHERE a = 1`
- ✅ `WHERE a = 1 AND b = 2`
- ✅ `WHERE a = 1 AND b = 2 AND c = 3`
- ✅ `WHERE a = 1 AND c = 3`（用了 a，c 用不上）

不能用索引的查询：
- ❌ `WHERE b = 2`（缺了 a）
- ❌ `WHERE c = 3`（缺了 a, b）

**记忆口诀**：**像电话号码一样，从左向右连续匹配**。

### 4.2 范围查询截断

```sql
-- 联合索引 (a, b, c)
WHERE a = 1 AND b > 5 AND c = 3
```

`b > 5` 是范围查询，**c 用不上索引**（B+ 树有序性被打破）。

**优化建议**：联合索引中**等值列在前，范围列在后**。

### 4.3 索引下推 (ICP, Index Condition Pushdown)

MySQL 5.6+ 优化：在索引层就过滤更多条件，减少回表次数。

```sql
KEY idx_name_age (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
```

- **无 ICP**：先按 `name LIKE '张%'` 拿到所有候选，全部回表，再过滤 age
- **有 ICP**：在索引里直接判断 `age = 20`，不满足直接丢弃，**减少回表**

EXPLAIN 中显示 `Using index condition`。

## 五、索引失效的 8 个经典场景（高频）

| # | 场景 | 错误示例 | 正确写法 |
|---|------|---------|---------|
| 1 | 函数操作 | `WHERE YEAR(create_time) = 2024` | `WHERE create_time >= '2024-01-01'` |
| 2 | 隐式类型转换 | `WHERE phone = 13800138000` (phone是varchar) | `WHERE phone = '13800138000'` |
| 3 | LIKE 左模糊 | `WHERE name LIKE '%三'` | `WHERE name LIKE '张%'` |
| 4 | OR 条件 | `WHERE id=1 OR name='张'` | UNION ALL 拆开 |
| 5 | `!=` / `<>` | `WHERE status != 1` | 改用 IN 列举可能值 |
| 6 | NOT IN / NOT EXISTS | 通常失效 | 改用 LEFT JOIN |
| 7 | 计算 | `WHERE age + 1 = 20` | `WHERE age = 19` |
| 8 | 不符合最左前缀 | (a,b) 索引下查 b | 调整索引或查询条件 |

**记忆口诀**：**「函数 + 计算 + 隐式转换 = 三大杀手」**。

## 六、实战：如何设计一个好索引

### 6.1 索引选择性（区分度）

```sql
SELECT COUNT(DISTINCT col) / COUNT(*) FROM table;
```

- 选择性 = 1：唯一索引（最高）
- 选择性 < 0.01：性别、状态等字段，**不适合单独建索引**
- 选择性 0.1 ~ 1：适合建索引

### 6.2 联合索引的字段顺序

**原则**（重要性递减）：
1. **等值 → 范围**
2. **高选择性 → 低选择性**
3. **覆盖更多查询场景**

### 6.3 索引数量原则

> 单表索引建议 **不超过 5 个**，每多一个索引：
> - 写入变慢（B+ 树维护成本）
> - 占用磁盘空间
> - 优化器选错索引概率↑

## 七、特殊索引

| 索引类型 | 用途 | 示例 |
|---------|------|------|
| **唯一索引** | 业务唯一约束 | `UNIQUE KEY uk_phone (phone)` |
| **前缀索引** | 长字符串字段省空间 | `KEY idx_url (url(20))` |
| **全文索引** | 文本搜索（少用，一般用 ES） | `FULLTEXT KEY (content)` |
| **空间索引** | GIS 地理坐标 | `SPATIAL KEY (location)` |
| **函数索引 (8.0+)** | 解决函数操作失效 | `((YEAR(create_time)))` |

## 八、易错点 / 拿分点

### ✅ 加分回答

1. **不要只说概念，要说底层数据结构**：B+ 树、双向链表、页的概念
2. **能讲出页大小（16KB）和数据量计算**：3 层 B+ 树存 2000 万
3. **主动提到索引下推、覆盖索引**
4. **讲索引失效时举具体例子**：函数、隐式转换的实际 SQL

### ❌ 容易踩坑

1. 把 InnoDB 的二级索引说成「指向数据」（实际指向主键）
2. 把哈希索引和 B+ 树搞混（InnoDB 用 B+ 树，Memory 引擎才用哈希）
3. 觉得「建得越多越好」（实际相反，写入会慢）

## 九、典型面试题速答

### Q1：索引为什么用 B+ 树？
A：B+ 树非叶子节点不存数据 → 单页存更多键 → 树更矮 → IO 少；叶子节点链表 → 范围查询友好；查询稳定都到叶子。

### Q2：聚簇索引和非聚簇索引区别？
A：聚簇索引叶子存整行数据，二级索引叶子存主键值。InnoDB 主键就是聚簇索引，普通索引查询需要「回表」。

### Q3：为什么推荐自增主键？
A：1）顺序写入避免页分裂；2）主键值小，二级索引存储成本低；3）符合 B+ 树插入特征。

### Q4：什么是覆盖索引？
A：查询字段全部在索引中，不需要回表。EXPLAIN 显示 `Using index` 即触发。

### Q5：索引失效有哪些场景？
A：函数、隐式类型转换、左模糊、OR、!=、范围列后续、不符合最左前缀。

### Q6：你设计索引会考虑什么？
A：1）覆盖核心查询；2）字段顺序按等值→范围、高选择性→低选择性；3）总数控制在 5 个内；4）避免冗余索引。

## 🎯 必背公式

```
B+ 树高度 ≈ log(N) / log(单页扇出)
单页扇出 ≈ 16KB / (索引列大小 + 6B 指针)
单表千万数据 → 树高度 3-4 层 → 主键查询 3-4 次 IO
```
