# 应用层：HTTP 与 DNS —— 面试高频考点

> 应用层是与开发最贴近的一层，HTTP/HTTPS、DNS解析、WebSocket几乎每场面试必问。

## 一、HTTP 协议核心

### HTTP 请求/响应格式

```
请求:
┌─────────────────────────────────────┐
│ GET /index.html HTTP/1.1            │ ← 请求行(方法 URL 版本)
│ Host: www.example.com               │ ← 请求头
│ User-Agent: Chrome/90               │
│ Accept: text/html                   │
│ Connection: keep-alive              │
│                                     │ ← 空行
│ (请求体，GET通常为空)                │
└─────────────────────────────────────┘

响应:
┌─────────────────────────────────────┐
│ HTTP/1.1 200 OK                     │ ← 状态行(版本 状态码 短语)
│ Content-Type: text/html             │ ← 响应头
│ Content-Length: 1024                │
│ Set-Cookie: session=abc123          │
│                                     │ ← 空行
│ <html>...</html>                    │ ← 响应体
└─────────────────────────────────────┘
```

### HTTP 状态码（必背）

| 分类 | 含义 | 常见 |
|------|------|------|
| 1xx | 信息性（请求已接收，继续处理） | 100 Continue, 101 Switching Protocols |
| 2xx | 成功 | **200 OK**, 201 Created, 204 No Content |
| 3xx | 重定向 | **301 永久重定向**, **302 临时重定向**, 304 Not Modified |
| 4xx | 客户端错误 | **400 Bad Request**, **403 Forbidden**, **404 Not Found** |
| 5xx | 服务端错误 | **500 Internal Server Error**, 502 Bad Gateway, **503 Service Unavailable** |

### HTTP 方法对比

| 方法 | 幂等 | 安全 | 用途 |
|------|------|------|------|
| GET | ✅ | ✅ | 获取资源 |
| POST | ❌ | ❌ | 创建资源/提交数据 |
| PUT | ✅ | ❌ | 全量更新资源 |
| DELETE | ✅ | ❌ | 删除资源 |
| PATCH | ❌ | ❌ | 部分更新资源 |
| HEAD | ✅ | ✅ | 只获取头部(不要body) |
| OPTIONS | ✅ | ✅ | 预检请求(CORS) |

## 二、HTTP 版本演进

| 对比项 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|--------|---------|---------|--------|--------|
| 连接 | 短连接(每次新建) | **持久连接(keep-alive)** | 多路复用 | QUIC(UDP) |
| 管道化 | 不支持 | 支持(但队头阻塞) | 真正并行 | 真正并行 |
| 头压缩 | 无 | 无 | **HPACK压缩** | QPACK |
| 服务器推送 | 无 | 无 | ✅ | ✅ |
| 队头阻塞 | 严重 | HTTP层有 | HTTP层无,TCP层仍有 | **完全解决** |
| 底层协议 | TCP | TCP | TCP | **UDP(QUIC)** |
| 连接建立 | 1-RTT | 1-RTT(复用连接) | 1-RTT | **0-RTT** |

**HTTP/2核心改进**：
```
1. 多路复用: 单连接上并行多个请求/响应（用Stream ID区分）
2. 头部压缩: HPACK算法，静态表+动态表+哈夫曼编码
3. 二进制帧: 替代文本格式，解析更高效
4. 服务端推送: 服务器主动推送资源(如推CSS/JS)
```

**HTTP/3为什么用UDP？**
```
TCP的根本问题: 队头阻塞在传输层(一个包丢失阻塞整个连接)
QUIC(UDP上层): 
  - 每个流独立，丢包只影响对应流
  - 0-RTT连接恢复(用缓存的TLS参数)
  - 内置TLS 1.3(合并握手)
  - 连接ID不绑定IP(网络切换不断连)
```

## 三、HTTPS（HTTP + TLS）

### HTTPS 建立连接完整过程

```
客户端                               服务端
  |                                     |
  |  ======= TCP 三次握手 =======       |
  |  ─── SYN ──────────────────→       |
  |  ←── SYN-ACK ──────────────        |
  |  ─── ACK ──────────────────→       |
  |                                     |
  |  ======= TLS 握手 =======          |
  |  ① ClientHello                     |
  |  (支持的TLS版本、密码套件、随机数)    |
  |  ──────────────────────────→       |
  |                                     |
  |  ② ServerHello + 证书 + 公钥        |
  |  ←──────────────────────────       |
  |                                     |
  |  ③ 客户端验证证书(CA签名链)          |
  |     生成预主密钥(Pre-Master Secret)  |
  |     用服务端公钥加密发送             |
  |  ──────────────────────────→       |
  |                                     |
  |  ④ 双方用相同材料生成会话密钥        |
  |     ChangeCipherSpec + Finished    |
  |  ←─────────────────────────→       |
  |                                     |
  |  ======= 加密HTTP通信 =======       |
  |  ──── 加密请求 ────────────→       |
  |  ←─── 加密响应 ────────────        |
```

### 对称加密 vs 非对称加密

| 对比 | 对称加密 | 非对称加密 |
|------|---------|-----------|
| 密钥 | 一把密钥加解密 | 公钥加密，私钥解密 |
| 速度 | 快（100-1000倍） | 慢 |
| 用途 | 数据加密传输 | 密钥协商、数字签名 |
| 代表 | AES, ChaCha20 | RSA, ECDHE |
| HTTPS中 | 加密实际HTTP数据 | TLS握手中协商对称密钥 |

**HTTPS为什么两种都用？**
```
非对称加密: 安全地交换对称密钥（解决"如何安全传递密钥"的问题）
对称加密: 实际加密数据（速度快，适合大量数据）
= "用非对称加密保护对称密钥" + "用对称密钥加密数据"
```

## 四、DNS 域名解析

### DNS 查询过程

```
用户输入 www.example.com
    ↓
① 浏览器DNS缓存 → 未命中
② 操作系统DNS缓存 → 未命中
③ 本地hosts文件 → 未命中
④ 向本地DNS服务器(递归解析器)发请求
    ↓
┌─ 本地DNS服务器 ──────────────────────────────────────┐
│ ⑤ 自身缓存 → 未命中                                   │
│ ⑥ 向根域名服务器查询 → 返回".com"的顶级域服务器地址      │
│ ⑦ 向.com顶级域服务器查询 → 返回"example.com"权威DNS地址  │
│ ⑧ 向权威DNS服务器查询 → 返回 www.example.com = 1.2.3.4 │
└──────────────────────────────────────────────────────┘
    ↓
⑨ 返回结果给客户端，并缓存(TTL)
```

### 递归查询 vs 迭代查询

| 对比 | 递归查询 | 迭代查询 |
|------|---------|---------|
| 发起方 | 客户端→本地DNS | 本地DNS→各级DNS |
| 特点 | "帮我问到底" | "我告诉你去问谁" |
| 负担 | 本地DNS承担全部 | 各级DNS各答各的 |

## 五、Cookie / Session / Token

| 对比 | Cookie | Session | Token(JWT) |
|------|--------|---------|------------|
| 存储位置 | 客户端浏览器 | 服务端内存/Redis | 客户端(Cookie/Header) |
| 安全性 | 较低(可被窃取/篡改) | 较高(仅存SessionID在客户端) | 较高(签名防篡改) |
| 跨域 | 受同源策略限制 | 受Cookie限制 | 灵活(放Header即可) |
| 服务端状态 | 无状态 | 有状态(存Session) | 无状态 |
| 扩展性 | - | 差(分布式需共享Session) | 好(无需服务端存储) |

## 六、WebSocket

```
HTTP:       请求-响应模式(半双工)，服务端不能主动推送
WebSocket:  全双工持久连接，双方可随时发送数据

建立过程 (基于HTTP升级):
  Client → Server:
    GET /chat HTTP/1.1
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Key: xxx

  Server → Client:
    HTTP/1.1 101 Switching Protocols
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Accept: yyy

  之后: 双方通过WebSocket帧通信（不再是HTTP）

适用场景: 聊天室、实时通知、在线游戏、股票行情
```

## 七、典型面试题 & 答案

### 题1：HTTP和HTTPS的区别？

**答**：
| 对比 | HTTP | HTTPS |
|------|------|-------|
| 安全性 | 明文传输，不安全 | TLS加密，防窃听/篡改/冒充 |
| 端口 | 80 | 443 |
| 性能 | 快(无加密开销) | 稍慢(TLS握手+加解密) |
| 证书 | 不需要 | 需要CA证书 |
| SEO | 搜索引擎不优先 | 搜索引擎优先收录 |

### 题2：从输入URL到页面显示的全过程？

**答**（经典综合题，涵盖所有网络层）：
1. **DNS解析**：域名→IP地址
2. **TCP连接**：三次握手建立连接
3. **TLS握手**：如果是HTTPS，协商加密参数
4. **发送HTTP请求**：构造请求报文发给服务器
5. **服务器处理**：后端业务逻辑+数据库查询
6. **返回HTTP响应**：状态码+响应头+响应体
7. **浏览器解析渲染**：HTML→DOM，CSS→CSSOM，合成渲染树→布局→绘制
8. **TCP断开**：四次挥手(或keep-alive复用)

### 题3：GET和POST的区别？

**答**：
| 对比 | GET | POST |
|------|-----|------|
| 语义 | 获取资源 | 提交/创建数据 |
| 参数位置 | URL查询字符串 | 请求体(Body) |
| 长度限制 | 有(URL长度限制~2KB) | 无(理论上) |
| 安全性 | 参数暴露在URL中 | 相对安全(Body中) |
| 幂等性 | 幂等(多次请求结果相同) | 非幂等 |
| 缓存 | 可被缓存 | 默认不缓存 |
| 书签 | 可加书签 | 不可加书签 |

**注意**：这些区别更多是**规范约定**而非技术限制。技术上GET也可以有Body，POST也可以幂等。

### 题4：304 Not Modified是什么意思？

**答**：服务器告诉客户端"资源未修改，你可以用本地缓存"。

**协商缓存过程**：
```
首次请求:
  响应: 200 OK + Last-Modified: Tue, 01 Jan 2024
  
再次请求:
  请求头: If-Modified-Since: Tue, 01 Jan 2024
  服务器检查: 资源未修改 → 返回304(无Body) → 客户端用缓存

或者用ETag:
  首次响应: ETag: "abc123"
  再次请求: If-None-Match: "abc123"
  服务器检查: ETag相同 → 304
```

## 八、面试加分点

### 常见追问与应对

```
Q: CDN的工作原理？
A: 将内容缓存到离用户最近的边缘节点
   用户请求 → DNS智能解析到最近CDN节点 → 缓存命中直接返回
   未命中则回源站获取并缓存

Q: 跨域问题怎么解决？
A: 同源策略: 协议+域名+端口三者相同才算同源
   解决: CORS(服务端设Access-Control-Allow-Origin头)
        JSONP(script标签不受同源限制，仅支持GET)
        Nginx反向代理(同源访问代理到不同后端)

Q: HTTP的keep-alive和WebSocket有什么区别？
A: keep-alive: 复用TCP连接发多个HTTP请求(仍是请求-响应模式)
   WebSocket: 升级为全双工协议，服务端可主动推送(不是HTTP了)
   keep-alive解决"连接复用"，WebSocket解决"服务端推送"
```
