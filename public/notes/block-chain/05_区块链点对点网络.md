## 5.1 P2P 网络架构

### 什么是 P2P 网络？

> P2P 网络（Peer-to-Peer）：点对点的网络结构，网络中每个节点既是资源提供者，也是资源获取者，所有节点处于平等状态。

**区块链的去中心化正是通过 P2P 网络实现的。**

### P2P 网络 vs 中心化网络

| 特征 | 中心化网络 | P2P 网络 |
|------|----------|---------|
| 控制方式 | 中心服务器控制 | 各节点对等 |
| 单点故障 | 存在 | 不存在 |
| 数据共享 | 通过中心转发 | 节点直接交换 |
| 去中心化程度 | 低 | 高 |

### P2P 网络的五大优势
1. 无单点故障风险
2. 抗审查性强
3. 带宽利用率高
4. 无中心化成本
5. 更强的隐私保护

## 5.2 节点类型

### 全节点（Full Node）

> 保存区块链中**所有交易信息**的节点，维护完整的区块链数据副本（从创世块到最新区块的全部账户交易历史）。

- 功能最丰富，安全性最高
- 管理用户钱包，可发布交易
- 能独立验证所有交易的合法性
- 占用存储空间大（比特币全节点需数百 GB）

### 轻节点（Light Node / SPV Node）

> 仅存储**区块头**信息和与自身相关的信息，不存储完整区块链数据。

**优点**：存储占用极小，适合移动端设备

**缺点**：无法独立验证交易数据真实性
- 轻节点不存储区块体中的交易
- 收到交易时，需借助**全节点确认**交易是否已上链

## 5.3 网络发现（Network Discovery）

### 如何加入比特币网络？

新节点加入网络必须与已存在的节点建立连接，连接到多个不同对等节点，才能构建通往网络的多条路径。

### 种子节点（Seed Nodes）

> 比特币网络中长时间稳定运行的节点，客户端内置列表，作为初始连接的入口。

### 网络发现要点

1. 节点自动记忆上次成功连接的节点，重启后快速重新连接
2. 节点失去连接时，自动尝试发现新节点
3. 连接成功后，节点向相邻节点广播自身 IP 地址
4. 新接入节点可向相邻节点请求已知节点的 IP 地址清单

## 5.4 Bloom 过滤器与简单支付验证（SPV）

### Bloom 过滤器的原理

> Bloom 过滤器：基于概率的过滤机制，在 SPV 节点中用于向全节点查询交易信息，**同时不暴露具体交易地址**，保护隐私。

#### 数据结构
- 一组**可变长度的二进制数组**（初始全为 0）
- 一组**可变数量的哈希函数**

#### 工作原理
1. 初始化：将 Bit 数组全部置为 0
2. 插入关键词：对关键词计算多个哈希值，将对应位置的 Bit 设为 1
3. 查询：对查询关键词计算哈希，若所有对应位均为 1，则"可能存在"；若有任一位为 0，则"必然不存在"

#### 关键特性

| 特性 | 说明 |
|------|------|
| **假阴性率为 0** | 返回"不存在"则必然不存在 |
| **假阳性率可控** | 返回"存在"可能误判 |
| **不支持删除** | 基础版本不支持（Bit 位可能被多个元素共享） |

#### 参数计算

```
Bit 数组大小：m = -(n · ln(p)) / (ln2)²
最优哈希函数个数：k = (m/n) · ln2

其中：
  n = 预期插入的元素数量
  p = 目标误判率（如 0.01 代表 1%）
```

**精度与隐私的权衡**：
- 数组越大、哈希函数越多 → 误判率越低，但暴露的信息越多
- 数组越小 → 隐私保护越好，但误判率越高

### 简单支付验证（SPV）

> SPV 节点通过 Bloom 过滤器向全节点查询特定交易，无需下载完整区块链。

**验证流程**：
1. SPV 节点将关心的交易哈希值插入 Bloom 过滤器
2. 将 Bloom 过滤器发送给全节点
3. 全节点将**通过过滤器的交易数据**、**交易所在区块头**、**每个交易的 Merkle 路径**返回给 SPV 节点
4. SPV 节点通过 Merkle 路径验证交易是否已上链

> SPV 节点无法通过 Bloom 过滤器删除关键词，只能发送新的过滤器替换旧的。

## 5.5 交易池（Transaction Pool）

### 作用

> 交易池是区块链交易的中转站，防止交易拥堵，维护区块链的交易秩序。

### 交易池中的两类数据

| 类型 | 说明 |
|------|------|
| 经验证的合法交易 | 等待被打包进区块 |
| 依赖未知交易的数据 | 暂时无法上链 |

### 比特币与以太坊的交易池

| 平台 | 合法交易存储 | 暂存交易存储 |
|------|------------|------------|
| **比特币** | `mempool` | `orphantx` 集合 |
| **以太坊** | `pending` 队列 | `queue` 队列 |

## 5.6 UTXO 数据库

### UTXO 的概念

> UTXO（Unspent Transaction Outputs，未花费的交易输出）：比特币区块链中的账户形式。

**特点**：
- 每笔交易由**交易输入**（指定 UTXO，表示花费）和**交易输出**（产生新 UTXO）组成
- 系统不保存"账户余额"，余额需通过 UTXO 推算

### UTXO 的运行原理

**示例**（铸币交易）：
- 哈希值：`4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b`
- 接收地址：`1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa`
- 2009-01-04，金额 50 BTC

**发起转账时，需提供**：
1. 交易哈希值
2. 输出索引值

### UTXO 集合的高效验证

- 系统将已有 UTXO 存储在**内存哈希表**中
- 验证交易时，直接查询哈希表，时间复杂度 O(1)
- 若输入不在 UTXO 集合中，交易直接判定为非法

### 交易生命周期

```
1. 交易创建 → 广播到全网
2. 挖矿节点接收 → 验证 UTXO 合法性
3. 通过验证 → 放入交易池（mempool）
4. 被矿工打包进区块 → 从交易池移除
5. 更新 UTXO 集合：花费的输出移除，新产生的输出加入
```

## 5.7 延伸阅读：Libp2p

### 什么是 Libp2p？

> Libp2p 是一套**标准化的 P2P 网络工具箱**，是模块化协议栈和工具集，并非单一的编程语言或协议。

**核心特点**：
- **模块化**：按需组合（如 Kademlia DHT 用于节点发现，TCP/WebRTC/QUIC 用于数据传输）
- **跨网络兼容**：支持 IPv4/IPv6、局域网、互联网、浏览器
- **跨语言实现**：Go、JavaScript、Python、Rust 等多语言版本，不同语言节点可互通

### 四大功能模块

| 模块 | 说明 |
|------|------|
| 节点路由 | 确定消息如何在节点间传递 |
| 节点管理 | 管理节点连接状态 |
| 节点记录 | 记录节点信息 |
| 节点发现 | 发现网络中的新节点 |

## 重点总结

| 知识点 | 要点 |
|--------|------|
| P2P 网络 | 去中心化基础，每个节点地位平等 |
| 全节点 | 存储完整区块链，安全性最高 |
| 轻节点（SPV）| 只存区块头，需借全节点验证 |
| 种子节点 | 网络入口，新节点初始连接目标 |
| Bloom 过滤器 | 概率型数据结构，保护轻节点隐私，有假阳性无假阴性 |
| 交易池 | 比特币用 mempool，以太坊用 pending 队列 |
| UTXO | 比特币账户模型，用哈希表高效查询合法性 |
