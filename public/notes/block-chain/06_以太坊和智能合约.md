## 6.1 共识算法基础

### 共识算法解决什么问题？

分布式系统面临两大不可靠性：

| 不可靠源 | 具体表现 |
|---------|---------|
| **节点不可靠** | 节点可能出错、崩溃，甚至存在恶意节点（拜占庭故障） |
| **网络不可靠** | 消息可能延迟或丢失 |

**网络模型**：
- **同步网络**（Synchronous）：消息在确定时间内到达
- **异步网络**（Asynchronous）：消息到达时间不确定

> 区块链（尤其是公链）必须完全考虑节点和网络的不可靠性。

---

### FLP 不可能定理

> **定理**（Fischer, Lynch, Patterson, 1985）：在异步系统中，即使只有**一个**错误节点，任何共识协议都存在**无法终止**的可能性。

**含义**：没有完美的共识算法，只能在安全性与活性之间权衡。

---

### CAP 原理

| 属性 | 说明 |
|------|------|
| **C（Consistency，一致性）**| 所有节点看到的数据一致 |
| **A（Availability，可用性）**| 每个请求都能得到响应 |
| **P（Partition Tolerance，分区容错性）**| 网络分区时系统仍能运行 |

> CAP 定理：三者**最多只能同时满足两个**。

**区块链的选择**：优先保证 **P + C**（分区容错 + 最终一致性），牺牲部分可用性。

---

### 公链共识机制

由于公链允许任何人自由加入或退出，需要应对：
- **故障节点**（Fault Node）：因错误无法正常工作的节点
- **作恶节点**（Byzantine Node）：主动发送错误信息、违反协议的节点

## 6.2 以太坊概述

### 以太坊介绍

| 项目 | 内容 |
|------|------|
| 英文名 | Ethereum |
| 创始人 | Vitalik Buterin（1994 年生，俄罗斯） |
| 创立时间 | 2013 年下半年提出构想，2014 年正式启动 |
| 核心特色 | 以太坊虚拟机（EVM） |
| 加密货币 | 以太币（Ether），全球第二大流通加密货币 |

**目标**：成为具有**分布式、公开透明、永不下线**特性的**全球计算基础设施**。

### 以太坊虚拟机（EVM）
- 完全隔离的沙箱环境
- 运行于 EVM 内部的代码**不能接触**网络、文件系统或其他进程
- 智能合约之间只有有限的接触

### 以太坊的技术公式

```
以太坊技术 = 区块链技术 + 智能合约
```

### 比特币脚本的局限性

| 缺陷 | 说明 |
|------|------|
| 缺少图灵完备 | 不支持循环语句 |
| 价值盲 | UTXO 不可分割 |
| 缺少状态 | UTXO 只能是已花费或未花费两种状态 |

以太坊内置**图灵完备**的编程语言（Solidity），解决以上所有限制。

## 6.3 以太坊挖矿与共识机制

### PoW 的问题（以比特币为例）

- 矿工只能通过耗费 CPU 算力反复尝试，无法投机取巧
- ASIC 矿机出现 → 算力集中于高端玩家 → 违背"人人参与"的初衷

### 以太坊初期共识（PoW + Ethash）

- 核心算法：**Ethash**（Dagger-Hashimoto 改良版）
- 关键设计：依赖 **1GB 预生成大型数据集（DAG）**
  - DAG 体积远超 ASIC 矿机内部寄存器，内存读写 I/O 成为瓶颈
  - 抵消了 ASIC 的算力优势，实现"算力去中心化"

**Ethash 挖矿流程**：
1. 计算种子（Seed），根据种子生成 **32MB Cache**
2. 根据 Cache 生成 **1GB DAG**（完整搜索空间）
3. 从 DAG 中随机选取元素进行哈希运算，寻找满足条件的 Nonce
4. Cache 和 DAG 每 1000 个块更新一次，DAG 大小每年增长约 7GB

### 以太坊 PoS 共识机制

PoS（Proof of Stake，权益证明）首次在 PeerCoin 中实现（2012 年）。

**核心思想**：用户证明持有一定数量的数字货币（"权益"），不需要大量算力即可参与创建区块（"铸币"）。

**币龄概念**：
> 币龄 = 持有数量 × 持有时间；创建新块后，币龄归零。

**PoS 相比 PoW 的优势**：

| 优势 | 说明 |
|------|------|
| 节约资源 | 无需消耗大量算力 |
| 提高攻击成本 | 攻击者需持有大量货币才能发动攻击 |
| 利益一致 | 大持有者更倾向维护系统安全 |

> 疑问解答：持有以太币多并不意味着永远获得记账权，因为币龄在创块后归零，防止垄断。

## 6.4 以太币（Ether）

| 特征 | 说明 |
|------|------|
| 初始发行量 | 众筹获得 7200 万枚（无需挖矿）|
| 每年增发上限 | 不超过初始量的 25%（约 1800 万枚）|
| 总量上限 | **无上限**（可无限通胀，与比特币 2100 万上限不同） |
| 功能定位 | 支付调用智能合约的交易费（Gas），不是纯货币 |
| 单位 | 最小单位 Wei；1 Ether = 10¹⁸ Wei |

## 6.5 以太坊账户

### 世界状态（World State）

> 所有以太坊账户的状态总集合，每个节点保存一份相同的副本，随交易不断更新。

**理解**：世界状态 = 每个人账户的状态的总集合

**状态机模型**：
```
交易发生 → 世界状态从 σt → σt+1
```

### 账户类型

| 类型 | 标识 | 特点 |
|------|------|------|
| **外部账户（EOA）**| 私钥 + 公开地址 | 由用户私钥控制，有余额，可发起交易 |
| **智能合约账户（CA）**| 只有公开地址，无私钥 | 由合约代码逻辑控制；不能主动发起交易，只能被外部账户调用 |

### 账户状态的四大元素

| 字段 | 说明 |
|------|------|
| **nonce** | 该账户已发送的交易总数 |
| **balance** | 以太币余额（持币数量） |
| **storageHash** | 存储区哈希值（智能合约专有，指向合约运行时的数据） |
| **codeHash** | 代码区哈希值（智能合约专有，指向合约字节码，只读不可更改） |

> 外部账户只有 nonce 和 balance，智能合约账户还有 storageHash 和 codeHash。

### 智能合约地址的生成

- 在创建合约时由代码**自动生成**，非外部创建
- 合约账户有公开地址，但**没有对应私钥**
- 因此：合约转出以太币不通过私钥签名，只由合约逻辑代码管理

## 6.6 以太坊交易

### 交易的本质

> 交易总是由**外部账户**发起，可以是：
> - 简单的以太币转账
> - 调用智能合约
> - 创建新的智能合约

### 交易的字段

| 字段 | 说明 |
|------|------|
| **nonce** | 发送方已发送的交易数量 |
| **GasPrice** | 每单位 Gas 的价格（由市场决定） |
| **Gas** | 交易消耗的最大 Gas 数量（用户估算） |
| **From** | 发送方地址 |
| **To** | 接收方地址（转账或合约地址；创建合约时可空） |
| **value** | 转移的以太币数量（以 Wei 为单位） |
| **data** | 数据字段（合约调用时包含函数名和参数字节码；纯转账时可空） |

**Gas 机制**：
```
交易费 = Gas × GasPrice
```
- 多余的 Gas 会退还给用户（assert 异常除外，会扣除所有剩余 Gas）
- 最贵：智能合约部署（需声明存储空间并初始化）
- 较便宜：普通转账

### 交易的三大特性

| 特性 | 说明 |
|------|------|
| **原子性**（Atomicity）| 要么全部执行，要么全部回滚，不会部分执行 |
| **串行执行**（Sequential）| 单一时刻只有一个交易被执行，无并行 |
| **顺序不确定**（Non-deterministic Order）| 交易进入区块链的顺序不由发送时间决定，受广播速度、Gas 费用等因素影响 |

### 三种主要交易类型

| 类型 | data 字段 | value 字段 |
|------|----------|-----------|
| 以太币转账 | 空缺 | 有值 |
| 调用智能合约 | 函数名 + 参数字节码 | 可有可无 |
| 创建智能合约 | 合约初始化字节码 | 可有可无 |

## 6.7 以太坊数据结构

### 三棵树

矿工打包交易时组织三棵 Merkle Patricia 树（MPT）：

| 树 | 存储内容 | 存储位置 |
|----|---------|---------|
| **交易树**（TransactionsRoot）| 当前区块的所有交易 | 链上存储 |
| **状态树**（StateRoot）| 所有账户的最新状态 | 节点本地 LevelDB |
| **收据树**（ReceiptsRoot）| 每笔交易执行产生的收据（含日志）| 节点本地 LevelDB |

**三棵树的根哈希**存入**区块头**，建立交易与区块头字段的映射，用于验证区块合法性。

---

### Merkle Patricia 树（MPT）

> MPT 是以太坊中大量使用的**键值存储数据结构**，兼具 Merkle 树的密码学安全校验和 Patricia 树的高效查询。

**特点**：
- 支持任意序列化字符串作为键和值
- 具有 Merkle 证明（完整性 + 存在性）
- 插入、删除、查询均为 O(log N) 时间复杂度

**节点逻辑结构**：索引（key）+ 路径（path）+ 数据（value）

---

### 状态树（State Tree）

- 所有账户的世界状态用 MPT 组织
- 每个账户位于叶节点
- 修改某账户 → 分支上层哈希值逐层更新 → 根哈希（StateRoot）变更
- StateRoot 存入区块头，随区块链推进不断变化

### 交易树（Transaction Tree）

- 每个区块有独立的交易树
- 包含当前区块打包的所有交易
- 交易排列顺序由矿工在打包时唯一确定

### 收据树（Receipt Tree）

- 每个区块有独立的收据树
- 存储交易执行期间产生的收据（类似超市小票）
- 包含智能合约执行产生的**日志（Log）**：
  - 日志产生方的地址
  - 日志话题（topics）
  - 日志数据（可选）

## 重点总结

| 知识点 | 要点 |
|--------|------|
| FLP 定理 | 异步系统中，只要有一个故障节点，共识可能无法终止 |
| CAP 原理 | 一致性/可用性/分区容错，最多满足两个 |
| EVM | 完全隔离的沙箱，运行智能合约 |
| Ethash | 内存密集型 PoW，抗 ASIC 矿机垄断 |
| PoS | 基于持币权益，无需消耗算力，引入币龄 |
| 世界状态 | 所有账户状态的集合，随交易持续更新 |
| 两类账户 | EOA（外部账户）vs CA（合约账户） |
| 账户四字段 | nonce, balance, storageHash, codeHash |
| 交易原子性 | 要么全执行，要么全回滚 |
| Gas 机制 | 交易费 = Gas × GasPrice |
| 三棵树 | 状态树、交易树、收据树，根哈希存入区块头 |
| MPT | 以太坊核心数据结构，高效键值存储 + Merkle 证明 |
