# 案例一：淘宝订单系统分库分表设计

> **来源场景**：阿里巴巴淘宝/天猫订单中心
> **数据规模**：日新增订单 1 亿+，历史订单百亿级
> **核心挑战**：单库单表无法承载超大规模交易数据，且需同时支持「买家维度」和「卖家维度」两种查询

---

## 一、应用场景

电商订单是典型的「写多读多 + 强一致性 + 长时间保留」业务，淘宝订单系统需要面对：

- **超大写入量**：双 11 大促峰值每秒数十万订单写入
- **双向查询需求**：
  - 买家侧：「我的订单」按 `user_id` 查询全部历史订单
  - 卖家侧：「商家订单管理」按 `seller_id` 查询全部订单
- **数据长期保留**：电子合同等场景要求订单数据至少保留 3 年
- **强一致性**：订单状态、金额、库存必须严格一致，不允许丢单

---

## 二、设计思路

### 2.1 单库单表的瓶颈

```
单表数据量 > 2000 万行 → 索引深度变深、查询变慢
单库 QPS > 5000 → 单机磁盘 IO/CPU 成为瓶颈
单实例容量 > 2TB → 备份/恢复时间不可接受
```

### 2.2 分片策略：双向冗余 + 基因分片

**核心方案：买家库 + 卖家库 双向冗余存储**

```
                ┌─────────────────────────┐
                │   订单写入服务（事务）   │
                └────────────┬────────────┘
                             │ 双写
              ┌──────────────┴──────────────┐
              ▼                             ▼
    ┌──────────────────┐          ┌──────────────────┐
    │  买家库 (1024库)  │          │  卖家库 (1024库)  │
    │  按 user_id 分片  │          │ 按 seller_id 分片 │
    └──────────────────┘          └──────────────────┘
```

**分片键计算**：
- 买家库：`db_index = user_id % 1024`，`tb_index = (user_id / 1024) % 8`
- 卖家库：`db_index = seller_id % 1024`，`tb_index = (seller_id / 1024) % 8`

最终物理表数：`1024 库 × 8 表 = 8192 张物理表`，单表稳定在千万行以内。

### 2.3 全局唯一订单号设计（基因分片）

订单号需要满足：
1. 全局唯一
2. 趋势递增（聚簇索引友好）
3. **包含分片基因**（拿到订单号即可定位到分片，避免广播查询）

```
订单号 = 时间戳(41位) + 机器ID(10位) + 序列号(7位) + user_id末4位(分片基因)
```

只要拿着订单号，就能直接计算 `db_index`，实现 **O(1) 定位**：

```sql
-- 通过订单号反查 user_id 后 4 位
-- 直接路由到对应分片，无需广播
SELECT * FROM order_buyer_xxxx WHERE order_id = '2024031912345678_1023';
```

## 三、技术亮点

### 3.1 双向冗余的双写一致性

订单写入流程使用 **本地消息表 + 异步补偿**：

```sql
-- 步骤1：写入买家库（事务A）
BEGIN;
INSERT INTO order_buyer (order_id, user_id, seller_id, ...) VALUES (...);
INSERT INTO local_message (msg_id, type, payload, status) VALUES (..., 'PENDING');
COMMIT;

-- 步骤2：异步任务扫描 local_message，写入卖家库
-- 步骤3：写入卖家库成功后，更新 local_message.status = 'DONE'
-- 步骤4：失败重试（指数退避），最终一致性
```

### 3.2 表结构（精简版）

```sql
CREATE TABLE order_buyer_0001 (
  id          BIGINT       PRIMARY KEY COMMENT '自增ID',
  order_id    VARCHAR(32)  NOT NULL    COMMENT '全局订单号(含分片基因)',
  user_id     BIGINT       NOT NULL    COMMENT '买家ID(分片键)',
  seller_id   BIGINT       NOT NULL    COMMENT '卖家ID',
  total_fee   DECIMAL(12,2) NOT NULL,
  status      TINYINT      NOT NULL    COMMENT '1待付款 2待发货 3待收货 4已完成',
  pay_time    DATETIME     NULL,
  create_time DATETIME     NOT NULL    DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME     NOT NULL    DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

  UNIQUE KEY uk_order_id (order_id),
  KEY idx_user_status (user_id, status, create_time),
  KEY idx_create_time (create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='买家维度订单表';
```

**索引设计要点**：
- `uk_order_id` 保证幂等
- `idx_user_status` 覆盖「我的订单」按状态筛选
- 不在 `seller_id` 上建索引（卖家查询走卖家库）

### 3.3 历史数据归档（冷热分离）

```
近 3 个月  → 热库（SSD，InnoDB）
3 个月-3 年 → 温库（机械盘，压缩表）
3 年以上   → 冷库（OSS 对象存储 + Hive 离线分析）
```

通过 **DTS 数据传输服务** 自动迁移，业务方查询时根据时间路由到对应存储层。

### 3.4 跨片查询解决方案

| 场景 | 方案 |
|------|------|
| 按买家查 | 直接路由到买家库 |
| 按卖家查 | 直接路由到卖家库 |
| 按订单号查 | 通过分片基因定位 |
| 多维度搜索（地址、商品名） | 异构到 Elasticsearch |
| 全局统计 | T+1 同步到 ODPS/Hive |

## 四、设计权衡与思考

### ✅ 优势

1. **线性扩展**：单分片承压能力固定，业务增长只需加分片
2. **查询无性能问题**：核心查询都能直接定位单分片
3. **故障隔离**：单库故障只影响 1/1024 用户

### ⚠️ 代价

1. **存储翻倍**：双向冗余使存储成本×2（实际通过冷热分离抵消）
2. **数据一致性复杂度**：依赖消息表 + 对账任务，运维成本高
3. **跨分片事务困难**：批量改价、退款链路必须使用最终一致性

### 💡 启示

> 大厂分库分表不是「分得越细越好」，关键是**找到业务的「分片基因」**——
> 像订单系统天然有 user_id 和 seller_id 两个维度，就用空间换时间做双向冗余；
> 像支付流水只有 user_id 一个维度，就单向分片即可。

---

## 五、可借鉴的设计模式

1. **基因分片**：把分片键编码进业务 ID，避免维护映射表
2. **双向冗余**：解决一对多查询场景的分片困境
3. **本地消息表**：用 MySQL 自身事务保证消息可靠投递
4. **冷热分级**：用存储成本换查询性能
