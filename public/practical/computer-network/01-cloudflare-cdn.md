# Cloudflare 全球 CDN 加速网络

## 应用场景

全球数百万网站依赖 Cloudflare CDN 加速静态与动态内容分发。当用户在巴西访问一个部署在美国的网站时，如果直接跨洋访问源站，RTT 可能高达 **200-300ms**；通过 CDN，用户请求被就近路由到圣保罗的边缘节点，延迟降至 **< 20ms**。

### 业务挑战

- **全球覆盖**：服务 200+ 国家用户，物理距离导致的延迟不可避免
- **海量并发**：峰值处理超 **5000万 HTTP 请求/秒**，单点架构不可能承载
- **动态内容**：不仅缓存静态资源，还需加速 API 请求和动态页面
- **安全防护**：DDoS 攻击峰值超 Tbps 级别，需在边缘就近清洗
- **协议演进**：HTTP/1.1 → HTTP/2 → HTTP/3(QUIC)，需要平滑升级

## 系统架构

```
用户浏览器
    ↓ DNS查询
┌──────────────────────────────────────────────────────────────────┐
│                    智能 DNS 调度层                                  │
│  • Anycast IP: 全球所有节点共享同一IP                               │
│  • BGP最短路径: 网络层自动路由到最近PoP                             │
│  • GeoDNS备选: 按地理位置返回最近节点IP                             │
└──────────────────────────────────────────────────────────────────┘
    ↓ 自动路由到最近PoP (Point of Presence)
┌──────────────────────────────────────────────────────────────────┐
│                    边缘节点层 (310+ 城市)                           │
│  • TLS终结: 在边缘完成TLS握手（减少一个RTT）                        │
│  • 缓存命中: 静态资源直接从边缘返回                                 │
│  • WAF/DDoS: 恶意流量在边缘就近清洗                                │
│  • HTTP/3 QUIC: 0-RTT连接建立                                     │
└──────────────────────────────────────────────────────────────────┘
    ↓ 缓存未命中时回源
┌──────────────────────────────────────────────────────────────────┐
│                    骨干网传输层                                     │
│  • 专用骨干网(Argo): 避开拥堵的公网路径                             │
│  • 智能路由: 实时探测选择最优路径                                   │
│  • 持久连接: 边缘与源站保持连接池，避免重复TCP握手                    │
└──────────────────────────────────────────────────────────────────┘
    ↓
┌──────────────────────────────────────────────────────────────────┐
│                    源站 (客户服务器)                                │
└──────────────────────────────────────────────────────────────────┘
```

## 设计思路

### 1. Anycast 路由（核心网络创新）

**传统方式 vs Anycast**：

| 对比 | 传统Unicast CDN | Anycast CDN |
|------|----------------|-------------|
| IP分配 | 每个节点不同IP，DNS返回最近IP | 所有节点共享同一IP |
| 路由决策 | 依赖DNS解析（可能不准） | BGP协议在网络层自动选最优路径 |
| 故障切换 | DNS TTL过期后才切换（分钟级） | BGP收敛自动切换（秒级） |
| DDoS防护 | 攻击集中在单IP/单节点 | 攻击流量自动分散到全球所有节点 |

**Anycast工作原理**：
```
全球所有PoP节点都宣告同一IP前缀: 1.1.1.0/24

用户ISP的BGP路由表:
  到 1.1.1.0/24 的路径:
    - via 新加坡PoP (AS path长度=2) ← 最短，选这条
    - via 美国PoP (AS path长度=4)
    - via 欧洲PoP (AS path长度=5)

结果: 用户流量自动被BGP路由到最近的PoP
```

### 2. HTTP/3 与 QUIC 协议优化

**为什么要从TCP迁移到QUIC**：

| 问题 | TCP的困境 | QUIC的解决 |
|------|----------|-----------|
| 连接建立慢 | TCP三次握手+TLS握手 = 2-3个RTT | 0-RTT恢复连接（首次1-RTT） |
| 队头阻塞 | 一个包丢失阻塞整个连接 | 多流独立，单流丢包不影响其他流 |
| 切换网络断连 | IP变化导致TCP连接失效 | Connection ID不绑定IP，无缝切换 |
| 拥塞控制僵化 | 内核实现，升级需改OS | 用户态实现，快速迭代(BBR) |

**QUIC连接建立流程**：
```
首次连接 (1-RTT):
  Client → Server: ClientHello + 支持的参数
  Server → Client: ServerHello + 证书 + 加密参数
  Client → Server: 开始发送加密数据
  (相比TCP+TLS的3个RTT减少了2个RTT)

恢复连接 (0-RTT):
  Client → Server: 用缓存的Session Ticket直接发送加密数据
  (无需任何握手往返！)
```

### 3. 缓存策略设计

**多级缓存架构**：
```
L1: 浏览器缓存（Cache-Control/ETag）
    ↓ 未命中
L2: 边缘PoP缓存（最近的CDN节点）
    ↓ 未命中
L3: 区域中心缓存（减少回源，合并请求）
    ↓ 未命中
L4: 源站
```

**缓存决策**：
| 内容类型 | 缓存策略 | TTL |
|---------|---------|-----|
| 静态资源(JS/CSS/图片) | 边缘缓存 + 长TTL | 1天~1年 |
| API响应 | 短TTL + stale-while-revalidate | 5-60秒 |
| 个性化内容 | 不缓存，但加速传输 | 0 |
| 视频流 | 分片缓存(Range请求) | 按热度动态调整 |

### 4. TLS 优化技术

**减少 TLS 延迟的手段**：

```
传统TLS 1.2: TCP握手(1 RTT) + TLS握手(2 RTT) = 3 RTT
TLS 1.3:     TCP握手(1 RTT) + TLS握手(1 RTT) = 2 RTT
QUIC + TLS:  合并握手 = 1 RTT（恢复时0 RTT）

额外优化:
  • OCSP Stapling: 证书状态由CDN预取，客户端不必查询CA
  • Session Ticket: 复用之前的TLS会话参数
  • 证书压缩: 减小证书传输体积
  • Early Hints (103): TLS握手期间就开始推送资源
```

## 技术亮点

### 亮点一：Anycast + BGP 的天然负载均衡与容灾

- **无需DNS切换**：节点故障时BGP自动撤回路由，流量秒级切到其他节点
- **DDoS天然分散**：攻击流量自动均摊到全球310+节点，单节点压力极小
- **无需GeoDNS**：网络层路由比DNS更精确（DNS可能被劫持或缓存过久）

### 亮点二：边缘计算(Workers)

- 在CDN边缘运行用户代码（JavaScript/WASM），而非仅缓存静态文件
- 实现：A/B测试、鉴权、请求改写、个性化内容——全在离用户最近的节点完成
- 延迟：代码在 < 50ms 内执行完毕，用户无感知

### 亮点三：BBR 拥塞控制替代 Cubic

```
传统TCP Cubic:
  基于丢包检测拥塞 → 带宽利用率仅60-70%（缓冲区未满就提前丢包）

Google BBR:
  基于带宽和RTT估算实际可用带宽 → 利用率提升至95%+
  特别适合高延迟长距离传输（跨洋链路）

Cloudflare在QUIC中默认启用BBR:
  实测: 长距离传输吞吐量提升 20-40%
```

### 亮点四：全链路加密 + 零信任

- 用户→边缘：TLS 1.3 / QUIC 强制加密
- 边缘→源站：也强制TLS（Authenticated Origin Pulls）
- 内部通信：mTLS双向认证
- 原则：即使内网也不信任，全链路加密

## 启发与思考

1. **网络层创新影响巨大**：Anycast一个路由技巧就解决了负载均衡+容灾+DDoS三个问题
2. **协议演进是渐进的**：HTTP/3不是推翻HTTP/2，而是解决TCP层面的根本限制
3. **靠近用户是王道**：物理距离带来的延迟是物理定律，只有"拉近距离"才能解决
4. **安全内嵌而非外挂**：TLS/WAF/DDoS防护作为基础设施，而非可选附加品
