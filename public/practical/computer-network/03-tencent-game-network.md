# 腾讯游戏全球低延迟网络架构

## 应用场景

腾讯旗下拥有《王者荣耀》《和平精英》《英雄联盟》等全球顶级竞技游戏，日活用户超**亿级**。实时对战类游戏对网络延迟极其敏感——玩家操作到画面反馈的延迟超过 **100ms** 就会感到"卡顿"，超过 **200ms** 则几乎无法正常游戏。

### 业务挑战

- **延迟敏感**：MOBA/FPS 游戏要求端到端延迟 **< 50ms**，丢包率 < 1%
- **全球对战**：不同国家/运营商的玩家需要在同一局游戏中低延迟通信
- **网络波动**：移动网络(4G/5G)切换基站、Wi-Fi信号波动导致丢包突增
- **运营商互联**：中国电信/联通/移动之间跨网延迟高达 50-100ms
- **成本控制**：专线昂贵，需要在成本和质量之间找平衡

## 系统架构

```
玩家客户端 (手机/PC)
    ↓
┌──────────────────────────────────────────────────────────────────┐
│                    接入层 (Access Layer)                           │
│  • 就近接入点: 全球 200+ 边缘节点                                  │
│  • 智能选路: 探测最优接入点(Ping最低)                               │
│  • UDP协议: 自定义可靠UDP (非TCP)                                  │
└──────────────────────────────────────────────────────────────────┘
    ↓
┌──────────────────────────────────────────────────────────────────┐
│                    加速网络层 (Relay Network)                      │
│  • 骨干专线: 核心城市间专线互联                                     │
│  • 智能路由: 实时探测延迟，选择最优中继路径                          │
│  • 多路冗余: 关键路径双发，选先到达的包                             │
└──────────────────────────────────────────────────────────────────┘
    ↓
┌──────────────────────────────────────────────────────────────────┐
│                    游戏服务器 (Game Server)                        │
│  • 帧同步/状态同步 逻辑                                           │
│  • 多地部署: 按玩家分布就近开服                                    │
│  • 房间路由: 匹配时考虑网络延迟最优                                 │
└──────────────────────────────────────────────────────────────────┘
```

## 设计思路

### 1. 为什么游戏不用 TCP？

**TCP vs UDP 在游戏场景的致命差异**：

| 对比项 | TCP | UDP (自定义可靠层) |
|--------|-----|-------------------|
| 连接建立 | 三次握手 (1.5 RTT) | 无连接，直接发送 |
| 丢包处理 | 必须重传且保序（队头阻塞） | 选择性重传，旧包可丢弃 |
| 拥塞控制 | 保守退让（丢包就降速） | 按游戏需求自定义速率 |
| 延迟 | 丢1个包阻塞整个流 | 独立帧互不影响 |
| NAT穿透 | 困难（有状态连接） | 容易（UDP打洞） |

**游戏的特殊需求**：
```
帧30: 玩家位置 (x=100, y=200)
帧31: 玩家位置 (x=105, y=198)  ← 如果帧30丢了
帧32: 玩家位置 (x=110, y=195)

TCP做法: 必须等帧30重传到达后才处理帧31/32 → 延迟++
游戏做法: 帧30过期了就丢弃，直接用最新的帧32 → 延迟不变
```

### 2. 自定义可靠 UDP 协议 (KCP/RUDP)

**协议设计**：

```
┌─────────────────────────────────────────────┐
│ 应用层: 游戏逻辑帧数据                        │
├─────────────────────────────────────────────┤
│ 可靠层(KCP): 选择性重传 + 拥塞控制             │
│  • conv (会话ID): 4 bytes                   │
│  • cmd (命令类型): 1 byte (数据/ACK/窗口)     │
│  • frg (分片号): 1 byte                     │
│  • wnd (接收窗口): 2 bytes                  │
│  • ts (时间戳): 4 bytes                     │
│  • sn (序列号): 4 bytes                     │
│  • una (已确认序号): 4 bytes                 │
│  • len + data                               │
├─────────────────────────────────────────────┤
│ UDP: 无连接传输                              │
├─────────────────────────────────────────────┤
│ IP: 网络层路由                               │
└─────────────────────────────────────────────┘
```

**KCP 相比 TCP 的关键优化**：

| 优化项 | TCP做法 | KCP做法 | 效果 |
|--------|--------|---------|------|
| RTO计算 | 保守(RTO=2×RTT) | 激进(RTO=1.5×RTT) | 重传更快 |
| 重传策略 | 超时才重传 | 快速重传(跳过2个ACK) | 减少等待 |
| ACK机制 | 累积确认 | 选择性确认(SACK) | 精确重传丢的包 |
| 拥塞退让 | 丢包减半窗口 | 不减半，仅轻微降速 | 保持发送速率 |
| 无延迟ACK | 200ms延迟确认 | 立即确认 | RTT估算更准 |

### 3. 智能路由选路

**问题**：公网路由不一定是最优路径（BGP基于策略，非最短延迟）。

```
公网路径: 深圳 → 广州IX → 上海IX → 北京 (延迟60ms)
专线路径: 深圳 → 北京 (延迟25ms)
中继路径: 深圳 → 香港中继 → 北京 (延迟30ms)

智能选路系统:
  • 每秒探测所有可能路径的延迟和丢包
  • 实时选择最优路径（可能随时间变化）
  • 无缝切换：切换路径时不中断连接(基于UDP无状态)
```

**跨运营商优化**：
```
中国网络痛点: 电信↔联通跨网延迟高达50-100ms

解决方案:
  • 在各运营商网内部署接入点
  • 电信玩家 → 电信接入点 → 专线 → 联通接入点 → 联通玩家
  • 避免经过拥堵的运营商互联点(IX)
  
效果: 跨网延迟从80ms降到20ms
```

### 4. 同步模型设计

**帧同步 vs 状态同步**：

| 对比 | 帧同步(Lockstep) | 状态同步(State Sync) |
|------|-----------------|---------------------|
| 传输内容 | 玩家操作指令 | 完整游戏状态 |
| 带宽需求 | 极小(几十字节/帧) | 较大(KB级/帧) |
| 延迟敏感度 | 极高(所有人等最慢的) | 中等(可插值预测) |
| 外挂难度 | 较高(服务器不算逻辑) | 较低(服务器权威) |
| 典型应用 | 王者荣耀(MOBA) | 和平精英(FPS) |

**帧同步的网络优化**：
```
问题: 一个玩家网络差 → 所有人卡顿（等待最慢的人）

乐观帧同步:
  - 服务器按固定频率(66ms/帧)推进，不等待
  - 网络差的玩家: 本地预测 + 收到服务器数据后回滚修正
  - 其他玩家: 不受影响，流畅进行

网络抖动缓冲(Jitter Buffer):
  - 客户端缓存2-3帧数据
  - 平滑网络抖动（包提前到就等一等，晚到也有缓冲）
  - 代价: 增加固定延迟(~50ms)，但消除卡顿
```

### 5. 弱网对抗策略

移动游戏面临严重的网络波动：

| 场景 | 问题 | 对抗策略 |
|------|------|---------|
| 基站切换 | 短暂断连(1-3秒) | 客户端状态预测+断线重连缓冲 |
| 信号差 | 丢包率20%+ | 前向纠错(FEC) + 多路冗余 |
| 延迟突增 | RTT从30ms跳到300ms | 本地预测 + 延迟补偿算法 |
| Wi-Fi干扰 | 间歇性丢包 | 冗余包(同一帧发两次) |

**前向纠错(FEC)**：
```
原始数据: [包1] [包2] [包3]
发送数据: [包1] [包2] [包3] [冗余包(由1+2+3异或生成)]

如果包2丢失:
  接收方用 包1 XOR 包3 XOR 冗余包 = 包2（恢复出来）
  无需等待重传！延迟不增加

代价: 带宽增加33% (3个数据包 + 1个冗余包)
适用: 实时性要求极高且能接受带宽开销的场景
```

## 技术亮点

### 亮点一：全球加速网络(GAAP)

- 腾讯自建全球加速网络，覆盖 200+ 节点
- 实时探测 + 动态选路：每5秒更新最优路径
- 效果：海外玩家访问国内服务器延迟降低 30-50%

### 亮点二：延迟补偿(Lag Compensation)

```
玩家A（延迟20ms）在T时刻开枪 → 服务器在T+20ms收到
玩家B（延迟80ms）在T时刻的位置，服务器要到T+80ms才知道

服务器做法（延迟补偿）:
  收到A的开枪请求时，回溯到A发出时刻的游戏状态
  检查A开枪时B的位置（T时刻-20ms=T-20ms时的B位置）
  判定是否命中

效果: 每个玩家看到的都是"我瞄准了就能打中"的体验
       即使网络延迟不同
```

### 亮点三：就近匹配(Latency-based Matchmaking)

- 匹配系统将网络延迟作为匹配因子之一
- 优先匹配同区域/同运营商玩家
- 如果跨区匹配，选择中间位置的服务器（公平延迟）

### 亮点四：协议降级与自适应

```
网络好时: UDP + 低冗余 + 高帧率(60fps)
网络差时: 自动降级
  - 增加FEC冗余度(33%→50%)
  - 降低帧率(60fps→30fps)
  - 压缩传输数据量
  - 增加客户端预测权重

自适应判断依据: 实时RTT + 丢包率 + 抖动
```

## 启发与思考

1. **TCP不是万能的**：特定场景下自定义UDP+可靠层比TCP性能好10倍
2. **公网路由不可控**：BGP选路基于策略而非延迟，游戏加速需要自建选路系统
3. **延迟由物理定律决定**：光纤中光速≈20万km/s，中国到美国最优也要70ms，所以必须就近部署
4. **冗余换延迟**：FEC用带宽换取丢包恢复零延迟，是实时通信的经典trade-off
