# 字节跳动四/七层负载均衡系统

## 应用场景

字节跳动旗下产品（抖音、今日头条、飞书、TikTok）日活用户超**10亿**，后端微服务集群规模达**百万级容器**。所有用户请求进入数据中心时，需要通过负载均衡器(Load Balancer)将流量均匀分发到后端服务实例，同时实现故障隔离、灰度发布和流量管理。

### 业务挑战

- **超高吞吐**：单集群入口流量达 **Tbps 级别**，传统 Nginx 瓶颈在百Gbps
- **低延迟转发**：LB自身引入的延迟需 **< 0.1ms**（不能成为瓶颈）
- **海量连接**：同时维护数亿 TCP 连接的状态
- **灵活调度**：支持按权重、灰度比例、用户特征精细路由
- **高可用**：LB自身不能成为单点故障，需要无缝容灾

## 设计思路

### 1. L4 负载均衡：DPDK 高性能转发

**为什么内核协议栈不够快？**

```
传统Linux网络路径:
  网卡 → 中断 → 内核协议栈(TCP/IP) → Socket → 用户态进程
  
瓶颈:
  • 中断开销: 每个包一次中断，高并发时CPU被中断占满
  • 内存拷贝: 内核态→用户态的数据拷贝
  • 锁竞争: 多核访问共享数据结构
  • 上下文切换: 内核态↔用户态切换开销

结果: 单核最多处理 1-2 Mpps (百万包/秒)
```

**DPDK (Data Plane Development Kit) 方案**：

```
DPDK网络路径:
  网卡 → 用户态驱动(PMD) → 用户态转发程序 → 网卡
  
优化:
  • 轮询代替中断(Poll Mode): 不产生中断开销
  • 零拷贝: 直接操作网卡DMA映射的内存
  • 无锁设计: 每个CPU核绑定独立的收发队列
  • Hugepage: 2MB大页减少TLB miss
  • Batch处理: 一次处理32/64个包

结果: 单核可处理 10-20 Mpps，比内核路径快10倍
```

**转发决策**：
```
收到数据包: (Src IP, Src Port, Dst IP=VIP, Dst Port=80)
查表:
  VIP:80 → Backend Pool = [10.0.1.1:8080, 10.0.1.2:8080, 10.0.1.3:8080]
  一致性哈希(Src IP + Src Port) → 选中 10.0.1.2:8080
修改:
  Dst IP: VIP → 10.0.1.2 (DNAT)
  Dst Port: 80 → 8080
转发给后端
```

### 2. 一致性哈希保证会话亲和

**问题**：同一用户的多次请求需要路由到同一后端（如TCP长连接、会话状态）。

**普通哈希的问题**：
```
hash(client_ip) % N = 后端节点编号

当后端从3台变为4台时:
  之前: hash(ip) % 3 = 1 → 节点B
  之后: hash(ip) % 4 = 2 → 节点C  ← 全部重新映射！
  
结果: 几乎所有连接断开
```

**一致性哈希**：
```
将0~2^32的哈希空间想象为一个环:

        节点A(hash=1000)
       /                \
  节点D(hash=8000)    节点B(hash=3000)
       \                /
        节点C(hash=6000)

客户端请求 hash=2500 → 顺时针找到第一个节点 → 节点B

添加节点E(hash=4000)时:
  只有 hash在3000~4000之间的请求 需要重新映射
  其他请求完全不受影响！
  
影响范围: 从100%降到 ~1/N
```

**虚拟节点**：
```
问题: 物理节点少时分布不均匀
解决: 每个物理节点对应100+个虚拟节点

节点A → hash(A#1), hash(A#2), ..., hash(A#150)
节点B → hash(B#1), hash(B#2), ..., hash(B#150)

效果: 哈希环上节点分布均匀，负载差异<5%
```

### 3. L7 负载均衡：基于内容的智能路由

L7 LB解析应用层协议，可以做更精细的流量分发：

**路由规则示例**：
```yaml
routes:
  # 按URL路径分流
  - match: { path_prefix: "/api/v2/" }
    route: { cluster: "service-v2" }
  
  # 按Header灰度
  - match: { headers: { "X-Gray": "true" } }
    route: { cluster: "service-canary", weight: 10% }
  
  # 按Cookie做A/B测试
  - match: { cookie: { "ab_group": "experiment" } }
    route: { cluster: "service-experiment" }
  
  # 默认路由
  - match: { any: true }
    route: { cluster: "service-stable" }
```

**灰度发布流程**：
```
阶段1: 新版本部署 → 灰度比例1%（内部员工）
       ↓ 观察指标正常
阶段2: 灰度比例10%（部分地区用户）
       ↓ 观察指标正常
阶段3: 灰度比例50%
       ↓ 观察指标正常
阶段4: 全量100%

任何阶段发现问题 → L7 LB秒级切回旧版本(无需重新部署)
```

### 4. 健康检查与故障隔离

```
主动健康检查:
  L4: TCP连接探测（能连通=健康）
  L7: HTTP GET /health 返回200=健康
  频率: 每3秒检查一次
  阈值: 连续3次失败 → 标记为不健康 → 从转发池摘除

被动健康检查:
  统计每个后端的实时错误率
  如果5xx比例 > 50% (5秒窗口) → 临时摘除
  恢复后逐步增加流量(类似TCP慢启动)

故障场景处理:
┌──────────────────────────────────────────────┐
│ 单实例故障 → 摘除该实例，流量转到其他实例      │
│ 机架故障   → 摘除该机架所有实例               │
│ 机房故障   → 跨机房调度(GSLB)                │
│ LB自身故障 → ECMP自动切换到其他LB节点         │
└──────────────────────────────────────────────┘
```

### 5. DSR（Direct Server Return）模式

**问题**：大文件下载/视频流场景中，响应数据远大于请求数据（不对称流量）。

```
普通NAT模式:
  Client → LB → Backend → LB → Client
  LB要转发全部返回流量 → LB成为带宽瓶颈

DSR模式:
  Client → LB → Backend → Client (直接回)
  LB只转发请求（小），响应直接绕过LB返回客户端
  LB带宽压力降低 90%+

实现:
  LB只修改目的MAC地址（不修改IP）
  Backend配置Loopback接口绑定VIP
  Backend直接用VIP作为源IP返回给Client
```

## 技术亮点

### 亮点一：ECMP + 一致性哈希的无状态L4集群

```
多台L4 LB组成集群:
  交换机通过ECMP(等价多路径)将流量分散到多台LB
  每台LB用相同的一致性哈希算法
  → 同一连接的包无论到哪台LB，都路由到同一后端
  → LB之间无需同步状态（无状态设计）
  → 任一LB故障，ECMP自动排除，其他LB接管
```

### 亮点二：连接表同步(Connection Tracking)

- L4 LB维护连接表(Src IP:Port → Backend IP:Port)
- 通过多播/组播在LB集群间同步连接表
- 主LB故障时，备LB有完整连接表，实现毫秒级接管（不断连）

### 亮点三：自适应限流

```
传统限流: 固定阈值(如1000 QPS)
  问题: 后端扩容了但限流没更新 → 浪费资源

自适应限流:
  实时监控后端: CPU利用率、请求队列长度、P99延迟
  当后端压力大时 → 自动收紧限流
  当后端空闲时 → 自动放宽限流
  
  公式: limit = f(CPU%, QueueLen, P99Latency)
```

### 亮点四：全链路灰度透传

- L7 LB注入灰度标记到HTTP Header
- 该标记通过RPC上下文在整条调用链路中透传
- 所有中间服务都感知灰度标记，路由到对应灰度版本
- 实现"从入口到数据库"的全链路灰度隔离

## 启发与思考

1. **性能需要跳出舒适区**：当内核协议栈成为瓶颈，就需要绕过它(DPDK/XDP)
2. **分层设计各司其职**：L4做粗粒度高性能转发，L7做细粒度智能路由
3. **一致性哈希是经典**：解决了"扩缩容时连接大规模中断"的问题
4. **无状态是王道**：无状态设计天然支持水平扩展和故障容灾
5. **灰度发布是安全网**：通过网络层控制流量比例，比重新部署安全得多
